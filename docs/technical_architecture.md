# 기술 아키텍처

## 1. 아키텍처 목표
- 빠르게 검증 가능한 MVP 구조를 유지합니다.
- 운영 확장 시 서비스 경계를 다시 나누기 쉬운 구조를 유지합니다.
- 사용자 앱, 관리자 앱, API, 수집기의 책임을 명확히 분리합니다.
- 공공데이터와 운영자 입력 데이터가 함께 들어와도 표준화된 스키마를 유지합니다.

## 2. 백엔드 선택 이유
WeddingMap 백엔드는 FastAPI를 사용합니다.

선택 이유는 다음과 같습니다.
- 타입 힌트 기반 개발과 Pydantic 검증 흐름이 명확합니다.
- OpenAPI 문서가 자동 생성되어 프론트엔드와 관리자 개발 속도가 빠릅니다.
- 수집기 역시 Python 생태계에 있기 때문에 데이터 처리와 운영 스크립트 연결이 자연스럽습니다.
- SQLAlchemy 2 계열과 함께 사용할 때 계층 분리가 단순하고 유지보수가 쉽습니다.

## 3. 구성 요소
### 사용자 앱
- 위치: `apps/web`
- 역할: 예비부부가 예식장을 탐색, 비교, 찜, 문의, 리뷰 작성하는 B2C 화면

### 관리자 앱
- 위치: `apps/admin`
- 역할: 운영자가 예식장 데이터, 가격, 리뷰, 문의, 수집 로그를 관리하는 내부 화면

### API
- 위치: `apps/api`
- 역할: 인증, 지역, 예식장, 비교, 예산 계산, 관리자 기능, 수집 실행 API 제공

### 수집기
- 위치: `services/ingestion`
- 역할: 공공데이터포털 또는 파일 기반 원천 데이터를 읽고 내부 표준 구조로 정규화

### 문서와 운영 스크립트
- 위치: `docs`, `scripts`
- 역할: 프로젝트 실행, 배포, 테스트, 운영 체크리스트와 인수인계 문서 제공

## 4. 데이터 흐름
1. 공공데이터포털 또는 파일 기반 원천 데이터를 수집기가 읽습니다.
2. 파서가 응답 구조를 WeddingMap 내부 예식장 표준 구조로 정규화합니다.
3. 병합 서비스가 중복 후보와 공공예식장 개수를 요약합니다.
4. 운영자 검수 또는 시드 로직이 실제 예식장 테이블 구조에 반영합니다.
5. API는 사용자 앱과 관리자 앱에 동일한 원천 데이터를 서로 다른 목적에 맞게 제공합니다.
6. 화면은 API 우선, 실패 시 제한적인 샘플 데이터 fallback 전략을 사용합니다.

## 5. 데이터베이스 전략
### 운영 기준
- PostgreSQL을 기본 저장소로 사용합니다.
- Redis는 수집 작업 큐, 캐시, 재시도 관리 구조 확장용으로 둡니다.

### 로컬 개발 기준
- Docker가 없는 환경에서도 빠르게 실행할 수 있도록 SQLite fallback을 지원합니다.
- 이 fallback은 개발 편의성을 위한 것이며, 운영 환경에서는 PostgreSQL 사용을 권장합니다.

## 6. 인증과 권한
- JWT 기반 액세스 토큰과 리프레시 토큰 구조를 사용합니다.
- 일반 사용자와 관리자 계정을 분리합니다.
- 관리자 API는 일반 사용자 API와 분리된 라우트 경로를 사용합니다.
- 비밀번호는 bcrypt 해시로 저장합니다.

## 7. 프론트엔드 구조
### 사용자 앱
- App Router 기반 페이지 구성
- `app` 디렉터리에 화면 라우트 배치
- `components`에 공통 UI 컴포넌트 배치
- `lib`에 API 호출, 타입, 계산 로직 배치

### 관리자 앱
- 운영 화면별로 대시보드, 예식장, 가격, 리뷰, 문의, 수집 로그를 구분
- API 호출 모듈과 표시용 컴포넌트를 분리
- 운영 화면은 최신성이 중요하므로 기본적으로 `cache: no-store` 기준을 사용

## 8. 수집기 구조
- `connectors`: 외부 API 연결 담당
- `parsers`: 원천 응답을 표준 구조로 변환
- `services`: 중복 탐지, 병합 요약, 향후 주소 정규화와 재시도 정책 담당
- `run_ingestion.py`: 파일 모드, 샘플 모드, 공공데이터포털 모드 진입점

## 9. 현재 한계와 의도
- 현재 수집기는 공공데이터포털의 대표적인 게이트웨이형 JSON 구조를 우선 지원합니다.
- 주소 정규화와 좌표 보정은 아직 완전 자동화되지 않았습니다.
- 관리자 화면은 필수 CRUD 중심이며, 대량 편집과 권한 세분화는 고도화 항목으로 남겨두었습니다.

## 10. 운영 확장 방향
- Redis 기반 비동기 수집 큐 추가
- 검색 전용 인덱스 도입
- 이미지 저장소 분리
- 관리자 권한 세분화
- 추천 로직 고도화
- 공공데이터와 운영자 입력 데이터의 버전 관리 추가
